# Public contribution design references

Checked on 2026-11-08. These are reference projects, not policies that h2a adopts automatically.

## T3 Code

At revision `1d78b3320328709d266ffd36af0dd75e614d14de`, the [contribution guide](https://github.com/pingdotgg/t3code/blob/1d78b3320328709d266ffd36af0dd75e614d14de/CONTRIBUTING.md) describes limited review capacity, approved scope for product changes, focused PRs, and evidence tied to the changed behavior. Vouch status does not exempt a contribution from triage; a separate explicit list controls exemptions. The guide also excludes code generated by specified models. h2a does not adopt that model restriction.

The inspected [PR Vouch workflow](https://github.com/pingdotgg/t3code/blob/1d78b3320328709d266ffd36af0dd75e614d14de/.github/workflows/pr-vouch.yml) uses `mitchellh/vouch` to maintain contributor-status labels. It does not close every unvouched PR. Its metadata automation is separate from testing a fork's code.

## Ghostty

At revision `c786f941f3b63f04a2c97d4c64cdd63cbdb589c4`, the [contribution guide](https://github.com/ghostty-org/ghostty/blob/c786f941f3b63f04a2c97d4c64cdd63cbdb589c4/CONTRIBUTING.md) requires first-time contributors to request a maintainer vouch before opening PRs. It routes initial reports and proposals through discussions, keeping issues actionable. It recommends reactions and discussion upvotes instead of repetitive support comments.

The [AI policy](https://github.com/ghostty-org/ghostty/blob/c786f941f3b63f04a2c97d4c64cdd63cbdb589c4/AI_POLICY.md) requires disclosure and human understanding of contributed code, with stricter rules for outside contributors. The [PR-check workflow](https://github.com/ghostty-org/ghostty/blob/c786f941f3b63f04a2c97d4c64cdd63cbdb589c4/.github/workflows/vouch-check-pr.yml) enables automatic closure through `mitchellh/vouch`. This is a stronger entry gate than T3 Code's contributor labels. Workflow source establishes configured behavior; this research did not operate either project's bots.

## Choices for h2a

h2a keeps first contributions open and accepts all harnesses under the same evidence requirements. Maintainers approve substantial work through `factory:ready`; there is no separate vouch registry, model denylist, automatic closure bot, or shared denouncement list. These choices keep the public entry path short while preserving review capacity.

The useful common practices are approved scope, evidence for the changed behavior, accountable operators, and a distinction between contributor history and permission to merge. h2a uses issue reactions as a demand signal. It keeps triage and ready work in the existing issue queue rather than adding another tracker or requiring Discussions at launch. See [governance](../../GOVERNANCE.md) and [the AI policy](../../AI_POLICY.md).

Public publication also changes the importer trust boundary. Two local designs were compared: journal-pinned identity with explicit adoption, and publisher-account-bound rediscovery with a journal migration. The journal design keeps the existing format and avoids a GitHub identity service call or GitHub App restrictions. Issue-body markers remain discovery hints, never authority to adopt a seed. The tradeoff is an explicit reconciliation step when the journal is missing.
