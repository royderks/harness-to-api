# Deployment choices

For the first release, run h2a and the signed-in harness on a laptop you control, with a **named Cloudflare Tunnel** for HTTPS access. When an always-on host is needed, move the same setup to a small Linux VM using Docker Compose and persistent storage. This keeps the CLI, its login and the gateway together. A tunnel provides ingress; it does not run the CLI. See [remote access](remote-access.md) for tunnel and client setup.

h2a starts a harness CLI as a subprocess for each request. It needs the CLI and its runtime installed, a writable home containing a working login, and persistent gateway key state (`HARNESS_API_STATE_DIR`, defaulting to `~/.harness-to-api`). A login can expire or require interactive reauthentication even when its files survive a restart. Plan how an operator will sign in and refresh it on the actual execution host; do not assume copying a login from another machine will work. Protect and back up both the harness state and gateway key state as sensitive data. Issue separate scoped gateway keys to clients; never give them the harness login.

## Recommended release path

1. Install and sign in to the supported CLI on the laptop, create a scoped h2a key, and run h2a on loopback. Create a named tunnel and point its hostname at that local port. The laptop and tunnel process must stay online. Use the key in the client's secret store and follow [remote access](remote-access.md) to verify model discovery, a streaming request, and rejection without a key.
2. For an always-on service, provision a small Linux VM and run the gateway and CLI with Docker Compose. Persist the CLI home and h2a state outside the container, use a dedicated service account, and keep the origin private behind a named tunnel. Pin the image and CLI versions, arrange backups and a reauthentication procedure, and test recovery after a container and VM restart. Compose packages the runtime reproducibly; it does not by itself preserve files or refresh credentials. A directly installed binary and process manager on the VM are also viable if container packaging is unnecessary.

A named tunnel requires a Cloudflare account and a hostname configured for the route. Cloudflare's [setup guide](https://developers.cloudflare.com/tunnel/get-started/) covers provisioning. Do not use a Quick Tunnel for this API: [Quick Tunnels do not support SSE and have a 200 in-flight request limit](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/). Cloudflare says [Tunnel streams responses marked `Content-Type: text/event-stream`](https://developers.cloudflare.com/tunnel/troubleshooting/); verify incremental delivery and long quiet periods end to end. [Proxy connection limits](https://developers.cloudflare.com/fundamentals/reference/connection-limits/) and any client or application timeout still apply; a named tunnel is not a promise of unlimited stream duration. A tunnel protects transport, not the host from actions an authenticated harness can perform.

## Cloudflare execution

A Worker can provide HTTP ingress or routing, but the existing subprocess-based server needs a Linux execution environment. [Cloudflare Containers](https://developers.cloudflare.com/containers/) can run a container image under Worker and Durable Object control on the Workers Paid plan. This is a possible hosting target, with additional integration: build a compatible image, route requests through the Worker and Durable Object, manage startup and restarts, restore state, and validate streaming, timeouts, CLI login and refresh. [Container disks are ephemeral by default](https://developers.cloudflare.com/containers/concepts/architecture/); Durable Object storage survives restarts, but is not automatically the container's home filesystem. Snapshots or external storage require explicit integration.

The [Sandbox SDK](https://developers.cloudflare.com/sandbox/concepts/lifetime/) is another way to run Linux workloads using container-backed sandboxes. Snapshots save filesystem state but not running processes, must be managed by the application, and expire after 30 days without use; mounted R2 data outlives instances. [R2 mounts have different rename, lock and permission behavior from a local disk](https://developers.cloudflare.com/sandbox/files/), so validate the CLI's credential writes and gateway key store rather than assuming compatibility. Restarts interrupt active requests and require the server to start again. These products make Cloudflare execution possible, but are more involved than the recommended VM for this stateful service.

## Vercel execution

[Vercel Functions can run OCI container images](https://vercel.com/kb/guide/does-vercel-support-docker-deployments), and Functions support streaming, but they are request-scoped and have [maximum durations](https://vercel.com/docs/functions/configuring-functions/duration). The [30-minute beta](https://vercel.com/changelog/vercel-functions-can-now-run-up-to-30-minutes) applies to Node.js and Python on Pro and Enterprise with Fluid compute; verify the applicable runtime and plan instead of assuming it applies to Rust or a container. The existing HTTP server can fit the container runtime, but its listen port must match Vercel's configured `PORT` (8787 for this image), and credentials and key revocations need durable storage shared across instances. The current Compose volumes are not available there; deploying the Dockerfile alone is insufficient. A Vercel frontend or Function may instead proxy to the VM, subject to its own request and streaming limits; that changes ingress, not where the CLI runs.

[Vercel Sandbox](https://vercel.com/sandbox) can run Linux commands and expose ports, so it is a possible execution environment with a controller to create or resume sessions, start h2a, route traffic, and handle interruptions. Sessions have finite durations: up to 45 minutes on Hobby and 24 hours on Pro or Enterprise. [Persistent sandboxes and Drives](https://vercel.com/kb/guide/vercel-sandbox-duration-and-persistence) can retain files across sessions, but processes must be restarted and credentials still need a secure refresh path. Test the full lifecycle and SSE route before relying on it as a service.

[Vercel Daemons](https://vercel.com/changelog/vercel-daemons-is-now-in-public-beta) are in public beta and run long-lived container workers. The [current Daemons limits](https://vercel.com/docs/daemons/limits) says the initial release cannot serve HTTP traffic and does not include persistent filesystem storage. Using one would therefore require a separate HTTP ingress, a work transport, durable state and changes to this server; it is not a direct deployment of the existing HTTP service.

## Validate the chosen deployment

These are deployment options, not tested turnkey integrations. Verify authentication, incremental SSE, long quiet requests, restart and state recovery, re-login, and key revocation on the actual route and host. Check the platform documentation for current plan limits.
