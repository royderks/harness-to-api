# First-use initialization

[Issue #11](https://github.com/royderks/harness-to-api/issues/11) introduces a foreground `h2a init` flow. It detects installed harnesses without inspecting credentials; login and model access remain unknown until an explicitly requested authenticated probe succeeds. The operator selects a provider and exact model, reviews the loopback endpoint, storage and limits, and can stop the server with Ctrl+C. Automation supplies provider, model, state directory, port and probe choice explicitly; JSON output is versioned NDJSON and never contains the secret or provider diagnostics.

The onboarding key expires one hour after creation and allows 20 accepted requests, 90 seconds per request, five requests per minute and one concurrent request. The server has a 90-second timeout and one concurrent request. These limits do not cap provider spending. A probe consumes an accepted request. Repeated initialization preserves the key, expiry and usage; it does not change client settings.

The state directory holds a nonsecret versioned profile and a separate protected client credential. The existing key store remains authoritative for the hash, policy and usage. The existing server admission lock owns the foreground lifecycle. After input validation and listener binding, setup prepares key identity, writes a pending profile, writes the credential, inserts the key record, and marks the profile ready. Recovery may complete a pending profile only when the credential and matching key record already exist. It must never recreate a missing record: absence could mean revocation. Explicit repair first marks the profile discarding, revokes only its recorded key, then removes its credential and profile. Corrupt identity requires manual repair.

Credential storage requires private ownership and permissions, safe path and link handling, and native Windows DACL creation and verification. Unsafe existing destinations fail closed. The listener is bound before onboarding artifacts are written, and no unrelated port occupant is contacted or terminated. No daemon, login, harness installation, tunnel, or client configuration change is introduced.

Two candidate designs were compared for first-use clarity, repeat and crash behavior, secret boundaries, maintenance, and proof. The parent scored A 18/25 and B 22/25; an independent ergonomic comparison scored A 17/25 and B 22/25. B was selected for its conservative handling of absent keys. A's retryable discarding phase is incorporated. Credential printing and catalog switching were rejected. These comparisons are design evidence, not security approval. Session-only credentials and a background broker were considered but do not meet the selected repeatability and simplicity goals as well.
