# v0.1.1 release candidate

Issue [#42](https://github.com/royderks/harness-to-api/issues/42) prepares a patch; it does not authorize publication. This candidate includes the reviewed fixes for connection pressure (#46) and version-independent example tests (#45), merged through source `cc1a389fa09a11ac71e011a3395280fd8c61bf52`. Release PR jobs explicitly check out and assert the PR head SHA; all six native jobs must pass on the final reviewed candidate commit. Each `build_*.txt` records the source commit and toolchain; each `verification_*.json` records the extracted archive checks. CI artifacts also contain the staged installer scripts tested with the matching archive. PR artifacts and local builds are candidates, not published assets.

Candidate notes: the patch bounds active TCP connections and recovers from transient accept failures, repairs example dependency regression tests, and adds one-command installers, an installed-harness chooser and missing-harness guidance, and tested SDK and sandbox examples. Offline fixtures do not prove live provider access. Binaries are unsigned; Linux requires a compatible glibc. Windows direct-child cancellation and the remaining platform limitations are described in [architecture](architecture.md). Windows candidate CI tests installation and refusal paths, but does not exercise the interactive chooser in a native terminal. Homebrew, npm, and Windows package managers remain separate follow-ups under #13.

## Publication handoff

1. After selecting and committing the final source, run the release workflow on that exact head and review all six native results, archive checksums, build metadata, and installer checks. Download and inspect the resulting bytes. Resolve any failures and obtain independent review.
2. Obtain separate owner authorization before creating a tag or draft release, publishing assets, or switching public installer defaults. Follow the release workflow and verify the attached bytes before publishing; do not replace assets of an existing release.
3. Once v0.1.1 is actually published, prepare a separate reviewed change to `install.sh` and `install.ps1`: replace their single `v0.1.0` version assignment with `v0.1.1`. The staged scripts in each candidate artifact show this exact patch. Update the public v0.1.0 installation instructions and published-binary smoke expectations in the same change, then run installer checks against the published assets. Until then, root installers and quickstart continue to target v0.1.0.
